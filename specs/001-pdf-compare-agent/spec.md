# 功能規格：大型 PDF 文件比較 Agent

**功能分支**：`001-pdf-compare-agent`

**建立日期**：2026-07-02

**狀態**：Draft

**輸入說明**：技術面試展示用專案——上傳兩份大型財務 PDF，透過 AI Agent 進行比較分析，並即時將推理過程展示於前端介面。

---

## 使用者情境與測試 *(必填)*

### 使用者故事 1 — 上傳 PDF 並發起比較分析（優先級：P1）

面試官或評審者開啟瀏覽器，上傳兩份大型 PDF 文件（例如兩份年報），點選「開始分析」，系統自動進行 PDF 前處理萃取，再透過 AI Agent 逐主題比較，並在頁面上即時串流顯示推理過程與最終差異報告。

**為何此優先級**：這是系統核心功能，其他功能均以此為基礎。沒有此流程，系統無法展示任何價值。

**獨立測試方式**：上傳兩份 PDF → 點選比較 → 畫面出現逐步推理訊息串流 → 最終顯示差異報告，整個流程可單獨驗證。

**驗收情境**：

1. **Given** 使用者已開啟應用程式首頁，**When** 上傳兩份各超過 50 頁的 PDF，**Then** 系統接受上傳並顯示兩份文件名稱及狀態
2. **Given** 兩份 PDF 已上傳完成，**When** 使用者點選「開始比較分析」，**Then** 頁面開始即時顯示 AI 推理過程訊息（如「正在抽取第一份文件內容…」「正在比較主題：服務範圍…」）
3. **Given** 分析進行中，**When** 推理步驟完成，**Then** 最終差異報告以結構化方式呈現於頁面（包含相同點、差異點、風險提示）
4. **Given** 上傳的 PDF 為掃描版（非純文字），**When** 系統進行前處理，**Then** 系統自動啟用 OCR 進行文字辨識後繼續分析流程

---

### 使用者故事 2 — 重複選取不同 PDF 組合進行多次比較（優先級：P2）

使用者在同一次工作階段中，希望多次選取不同的兩份 PDF 進行比較，而不需要重新整理頁面或重新上傳所有文件。

**為何此優先級**：面試展示時常需要快速切換比較組合，提升操作流暢度。

**獨立測試方式**：上傳 3 份 PDF → 選取 PDF-A 與 PDF-B 比較 → 完成後 → 重新選取 PDF-A 與 PDF-C 比較 → 系統正確執行第二次分析。

**驗收情境**：

1. **Given** 使用者已上傳多份 PDF，**When** 在 PDF 清單中重新勾選不同組合，**Then** 系統使用新選定的兩份文件發起新一輪比較
2. **Given** 前一次比較已完成，**When** 使用者選取新組合並點選「開始比較」，**Then** 舊的分析結果被清空，新的推理過程從頭顯示

---

### 使用者故事 3 — 關閉頁面後自動清除 PDF（優先級：P3）

使用者關閉瀏覽器分頁或整個視窗後，伺服器端儲存的 PDF 檔案自動刪除，不佔用持久儲存空間。

**為何此優先級**：確保展示環境整潔，避免敏感財務文件殘留在伺服器，但不影響核心比較功能。

**獨立測試方式**：上傳 PDF → 關閉瀏覽器 → 等待幾秒 → 確認伺服器端 PDF 已被刪除。

**驗收情境**：

1. **Given** 使用者已上傳 PDF 並離開頁面（關閉分頁），**When** 工作階段逾時或 beforeunload 事件觸發，**Then** 後端自動刪除該工作階段對應的所有 PDF 檔案
2. **Given** PDF 已自動清除，**When** 同一使用者重新開啟應用，**Then** 先前上傳的 PDF 不再顯示，需重新上傳

---

### 邊界情況

- 上傳超大 PDF（例如 500 頁）時，系統不應逾時或崩潰，應分段處理並持續回報進度
- 兩份 PDF 章節結構完全不同時，AI Agent 應能自動發現對應主題，而非硬對齊頁碼
- 掃描品質極差（低解析度、有浮水印）的 PDF 應有明確的錯誤提示或降級處理
- 同一工作階段重複上傳相同檔名的 PDF 時，系統應允許覆蓋或以區分命名處理
- 網路中斷導致分析串流中斷時，頁面應顯示錯誤狀態，允許使用者重試

## 需求 *(必填)*

### 功能需求

- **FR-001**：系統 MUST 支援同時上傳最多 10 份 PDF 文件（每份上限 100MB）
- **FR-002**：系統 MUST 支援純文字 PDF 與掃描版 PDF（自動 OCR 處理）
- **FR-003**：系統 MUST 在分析前對 PDF 進行前處理萃取：文字抽取 → 章節/段落識別 → 分段 Chunking，不得將完整 PDF 直接送入 LLM
- **FR-004**：系統 MUST 透過 Server-Sent Events（SSE）或 WebSocket 即時串流回傳 AI 推理步驟至前端
- **FR-005**：使用者 MUST 能夠從已上傳的 PDF 清單中任意選取 2 份，發起比較分析
- **FR-006**：系統 MUST 輸出結構化差異報告，包含：相同點、差異點、風險提示三個區塊
- **FR-007**：系統 MUST 在使用者工作階段結束（關閉頁面）後自動清除所有上傳的 PDF 檔案
- **FR-008**：系統 MUST 提供 Docker Compose 設定，可一鍵啟動前端、後端服務
- **FR-009**：前端 MUST 以 React 實作，顯示 PDF 清單、推理過程串流、最終差異報告
- **FR-010**：後端 MUST 以 FastAPI 實作，提供 PDF 上傳、分析觸發、串流回應 API

### 關鍵實體

- **PDF 文件（PDFDocument）**：名稱、上傳時間、處理狀態（pending / processing / ready）、工作階段 ID
- **工作階段（Session）**：工作階段 ID、建立時間、關聯的 PDF 清單、到期時間
- **比較任務（ComparisonJob）**：任務 ID、選定的兩份 PDF ID、狀態（queued / running / done / error）、推理步驟串流、最終報告
- **推理步驟（ReasoningStep）**：步驟編號、類型（info / thinking / result）、內容文字、時間戳記

---

## 成功標準 *(必填)*

### 可量化目標

- **SC-001**：使用者從點選「開始比較」到看到第一則推理訊息，等待時間不超過 5 秒
- **SC-002**：系統能夠成功處理單份超過 100 頁的 PDF，不發生逾時或崩潰
- **SC-003**：推理過程串流訊息在後端產生後，1 秒內出現於前端畫面
- **SC-004**：使用者關閉頁面後，伺服器端 PDF 檔案在 30 秒內完成清除
- **SC-005**：面試評審能夠透過前端畫面清楚理解 AI 分析的逐步推理過程（以可讀文字呈現，非技術日誌）
- **SC-006**：同一工作階段內，使用者可成功執行至少 3 次不同 PDF 組合的比較分析

---

## 假設

- 使用者為技術面試評審，具備基本電腦操作能力，但不需了解 AI 或程式實作細節
- 系統僅需支援單一使用者同時操作（非多人並發場景），MVP 階段不需水平擴展
- PDF 語言以繁體中文為主，亦可能包含英文財務數據
- LiteLLM Proxy 端點（`https://lllm.xsong.us`）可正常存取，不需在本專案中部署 LiteLLM 服務本身
- 工作階段識別採用瀏覽器 sessionStorage 或 Cookie，不需使用者登入驗證
- 前處理分段（Chunking）策略以章節為單位，每段不超過 4,000 tokens
- MVP 階段不需要持久化歷史比較記錄，每次工作階段獨立
